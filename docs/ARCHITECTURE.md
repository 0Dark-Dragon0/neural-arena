# Neural Arena: Systems Architecture Guide

This document provides a highly technical, deep-dive breakdown of Neural Arena’s 6-layer architecture. Every subsystem is designed around the core commitments of **mathematical determinism, immutable event sourcing, and high-fidelity observability**.

```
┌───────────────────────────────────────────────────────────────────┐
│                      Mission Control Dashboard                    │
│  State: useDashboardStore | useReplayStore | useReplayLibrary    │
├───────────────────────────────────────────────────────────────────┤
│                   Socket.IO Transport Protocol                    │
├───────────────────────────────────────────────────────────────────┤
│                   Multi-Agent Turn Orchestrator                   │
├───────────────────────────────────────────────────────────────────┤
│                Cognition & Prompt Adaptation Pipeline             │
├───────────────────────────────────────────────────────────────────┤
│                  LLM Provider Abstraction Layer                   │
├───────────────────────────────────────────────────────────────────┤
│                   Deterministic Simulation Engine                  │
│  EventBus ──► EventStore ──► WorldStateTree ──► SimulationClock   │
└───────────────────────────────────────────────────────────────────┘
```

## 1. Layer 1 — Deterministic Simulation Engine

The engine is the authoritative state broker of Neural Arena. It does not contain any strategic or game-specific rules (e.g., chess moves). Instead, it acts as a generic event processor.

### Core Engine Classes

#### A. EventBus (`src/engine/EventBus.ts`)
The `EventBus` handles publish/subscribe operations within the server. To prevent accidental mutations of events, all payloads are deep-cloned and frozen (`Object.freeze`) before delivery.
* **Monotonic Sequencing**: Every event is stamped with a sequential index (`sequence`) and a timestamp.
* **Causal Linkage**: Every event generated by another carries a `causedByEventId` pointer, constructing a complete causal chain.

```typescript
export interface RuntimeEvent {
  eventId: string;          // Deterministically generated UUID
  type: string;             // Event catalog identifier
  tick: number;             // Active simulation tick
  simulationTimeMs: number; // Ticks × tickRate
  sequence: number;         // Monotonic sequence identifier
  data: Record<string, any>;// Event-specific data
  causedByEventId?: string; // Causal parent event UUID
}
```

#### B. EventStore (`src/engine/EventStore.ts`)
An append-only, in-memory array that archives every event emitted since simulation startup. This log is the single source of truth.
* **Serialization**: On simulation teardown, the EventStore is serialized into a standard `.neural-arena.json` JSON block for export.
* **Restore**: To resume or replay, the EventStore is loaded, and events are processed sequentially from index `0` to restore state.

#### C. WorldStateTree (`src/engine/WorldStateTree.ts`)
A Merkle-like hierarchical state structure that hashes the simulation state at each transition.
* **State Identification**: After each action is applied, the world state compiles a structural representation (e.g., a FEN string in chess) and calculates its SHA-256 hash.
* **Node Linking**: Every state is saved as a tree node linked to its parent hash, supporting rollbacks, parallel branching, and fast state-diffing.

```typescript
export interface WorldStateNode {
  stateHash: string;        // SHA-256 of the structural representation
  parentHash: string | null;// Pointer to parent state hash
  tick: number;             // Active simulation tick
  representation: string;   // Domain-specific state string (e.g., FEN)
  metadata: Record<string, any>;
}
```

#### D. SimulationClock (`src/engine/SimulationClock.ts`)
Differentiates between **simulation time** (derived purely from `tick × tickRate` and entirely deterministic) and **wall-clock time** (used only for monitoring). This decouples runtime calculations from CPU throttling or execution delays.

## 2. Layer 2 — Provider Abstraction Layer

Neural Arena isolates the simulation loop from the specifics of model APIs.

```
                  ┌──────────────────────────────┐
                  │      Provider Interface      │
                  │   (API Client, Tokenizers)   │
                  └──────────────┬───────────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│    NVIDIA NIM    │    │    OpenAI API    │    │   Local Server   │
│  (Gemma/LLaMA)   │    │      (GPT)       │    │  (Ollama/vLLM)   │
└──────────────────┘    └──────────────────┘    └──────────────────┘
```

### Components

#### API Client (`src/core/api-client.ts`)
A unified HTTP client equipped with:
* **Exponential Backoff**: Automatic retry patterns with jitter for standard provider errors (e.g., rate limits, server overloads).
* **Timeout Escalation**: Increases request timeout durations on consecutive failures before triggering a fallback.

#### Provider Tracker (`src/core/provider-tracker.ts`)
Tracks request latency and error rates for each provider. If a model fails consistently, the tracker signals the orchestrator to engage fallback routines.

#### Normalization (`src/core/normalizer.ts`)
Formats varied API outputs into a standard format. It handles system roles for models that do not support them by folding system instructions directly into user prompt matrices.

## 3. Layer 3 — Cognition & Prompt Adaptation Pipeline

This layer manages agent thinking and handles errors before submitting actions to the engine.

### Cognitive Context Matrix (`src/cognition/ContextCompiler.ts`)
Before dispatching a prompt, the system compiles a structured matrix of inputs:

```typescript
export interface CognitiveContextMatrix {
  persona: PersonaBlock;          // Character details & risk profiles
  worldState: WorldStateBlock;    // Current world representation (e.g., board FEN)
  tacticalMemory: MemoryBlock;    // Log of recent move rejections and failures
  retrieval: RetrievalBlock;      // Context placeholder for RAG hooks
  constraints: ConstraintBlock;   // JSON rules, schemas, & anti-cheat guidelines
  legalMoves: LegalMovesBlock;    // List of allowed actions from the world state
}
```

### Prompt Escalation Engine (`src/cognition/PromptCompiler.ts`)
If a model generates an illegal action, Neural Arena applies progressive prompt corrections on the next retry.

```
Level 0: Standard Prompt (Structured parameters)
   │
   ▼ (Invalid move or malformed JSON)
Level 1: Correction Insert ("Your action was rejected because...")
   │
   ▼ (Repeated failure)
Level 2: Strict Constraint ("You must select from the following legal move list...")
   │
   ▼ (Critical failure)
Level 3: Minimal Deterministic (Minimal text, index-mapped legal actions)
   │
   ▼ (Extreme failure)
Level 4: Forced Constrained Fallback (Bypasses LLM, engine executes random legal action)
```

## 4. Layer 4 — Multi-Agent Turn Orchestrator

Coordinates turn schedules and manages agent states.

```
        ┌──────────────────┐
        │      IDLE        │
        └────────┬─────────┘
                 │ Agent turn begins
                 ▼
        ┌──────────────────┐
        │    THINKING      │◄──────────────────────────┐
        └────────┬─────────┘                           │
                 │ ContextCompiled & API Request       │ Rejection / Retry
                 ▼                                     │
        ┌──────────────────┐                           │
        │AWAITING_RESPONSE │                           │
        └────────┬─────────┘                           │
                 │ API Response Received               │
                 ▼                                     │
        ┌──────────────────┐                           │
        │   VALIDATING     │───────────────────────────┘
        └────────┬─────────┘
                 │ Intent Approved
                 ▼
        ┌──────────────────┐
        │    ACCEPTED      │
        └──────────────────┘
```

### Turn State Machine Transitions Table

| Current State | Trigger Event | Transition To | Actions Executed |
| :--- | :--- | :--- | :--- |
| **IDLE** | `TURN_STARTED` | **THINKING** | Compiles Context Matrix; sets timeout timer. |
| **THINKING** | `CONTEXT_COMPILED` | **AWAITING_RESPONSE** | Dispatches API call; registers request ID. |
| **AWAITING_RESPONSE** | `RESPONSE_RECEIVED` | **VALIDATING** | Parses response payload; performs schema check. |
| **AWAITING_RESPONSE** | `API_TIMEOUT` | **THINKING** (Retry) | Increments error counter; adjusts backoff delay. |
| **VALIDATING** | `INTENT_INVALID` | **THINKING** (Retry) | Appends error to Tactical Memory; escalates Level. |
| **VALIDATING** | `INTENT_VALID` | **ACCEPTED** | Commits action; triggers World State update. |
| **ACCEPTED** | `TURN_FINISHED` | **IDLE** | Clears turn memory; transfers control to next agent. |

### Turn Orchestrator (`src/core/turn-orchestrator.ts`)
Drives the loop sequence:
1. **Cooldown Buffer**: Calculates delays based on API health and latency logs.
2. **Context Compilation**: Assembles the prompt payload.
3. **Inference Dispatch**: Sends requests with timeout monitors.
4. **Anti-Cheat Validation**: Checks schema conformance, extracts moves, and validates legality.
5. **Execution**: Submits valid moves to the IntentGateway.

## 6. Layer 6 — Dashboard (Mission Control UI)

A React application utilizing Zustand stores to manage visual states.

### Zustand Store Interface Specifications

#### A. Dashboard State (`src/dashboard/src/state/useDashboardStore.ts`)
Manages real-time streaming connections, dashboard settings, and UI visual states.
```typescript
interface DashboardState {
  isConnected: boolean;
  activeSimulationId: string | null;
  activeDomain: string | null;
  tickRateMs: number;
  isPaused: boolean;
  
  // Provider settings
  providerProfiles: Record<string, any>[];
  activeProfileId: string | null;
  
  // Connection actions
  connect: (url: string) => void;
  disconnect: () => void;
  startSimulation: (config: any) => void;
  pauseSimulation: () => void;
  resumeSimulation: () => void;
}
```

#### B. Replay State Reconstruction (`src/dashboard/src/state/useReplayStore.ts`)
Calculates active state during playback using a pure reconstruction function:
$$\text{ReplayState}(E, c) = \text{applyEvents}(\text{InitialState}, E[0 \dots c])$$

Because `applyEvents` is pure and deterministic, scrubbers can traverse history in real time without introducing state leaks.
```typescript
interface ReplayState {
  events: RuntimeEvent[];
  cursor: number;               // Current index in the events array
  playbackSpeed: number;        // 0.5x, 1.0x, 2.0x, 4.0x
  isPlaying: boolean;
  
  // Navigation actions
  loadEvents: (events: RuntimeEvent[]) => void;
  seekTo: (index: number) => void;
  stepForward: () => void;
  stepBackward: () => void;
  play: () => void;
  pause: () => void;
  setSpeed: (speed: number) => void;
}
```

#### C. Replay Library Store (`src/dashboard/src/state/useReplayLibrary.ts`)
Manages saved simulation directories with database operations.
```typescript
export interface ReplayEntry {
  id: string;
  name: string;
  createdAt: string;
  eventCount: number;
  moveCount: number;
  durationTicks: number;
  agents: { white: string; black: string };
  result: 'checkmate' | 'stalemate' | 'draw' | 'timeout' | 'in-progress' | 'unknown';
  tags: string[];
  sizeBytes: number;
}

export interface ReplayLibraryState {
  entries: ReplayEntry[];
  isLoading: boolean;
  loadLibrary: () => Promise<void>;
  saveReplay: (name: string, events: RuntimeEvent[], metadata: Partial<ReplayEntry>) => Promise<string>;
  deleteReplay: (id: string) => Promise<void>;
  renameReplay: (id: string, name: string) => Promise<void>;
  addTag: (id: string, tag: string) => Promise<void>;
  removeTag: (id: string, tag: string) => Promise<void>;
}
```
*   **Zustand Sync**: Pushing reconstructed states into the dashboard allow the entire panel array (Move History, SVGs, Diagnostics) to render correct histories without requiring specialized replay logic in the UI components.
